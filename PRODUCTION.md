# Production deployment

## Administrator access

Bookmark **https://YOUR-WEBSITE/sign-in**. Staff accounts proceed to
**/account/content**. The public navigation links to the client portal at /account. Signed-out visitors are sent to /sign-in, which also offers account registration. Authentication pages are excluded from indexing.
Hiding navigation is not an access control: Django verifies staff permissions on
every content write. Existing member accounts and their direct routes still work.

Use **https://YOUR-API/admin/** for full Django administration and media uploads.
Set the frontend's server-only DJANGO_ADMIN_URL to this browser-accessible URL.
Only existing Django staff accounts can manage website content; create the first
administrator with:

    python manage.py createsuperuser --settings=config.settings

Protect /admin/, /api/auth/login/, /api/token/ and frontend sign-in POSTs with
per-client rate limits at your trusted ingress. Restrict Django admin to your
organization's VPN or identity-aware access proxy where available.

## Django service

Use Python 3.12, PostgreSQL and the pinned requirements.txt. Populate hosting
environment variables using perpetual-api/.env.production.example; keep real
secrets out of Git. Set DJANGO_ENV=production and DJANGO_SETTINGS_MODULE=config.settings. This selects
validated config.production. Missing credentials, insecure origins, weak keys,
wildcard hosts and non-PostgreSQL URLs prevent startup. Local development uses DJANGO_ENV=development with config.settings, or the
local-only manage_local.py launcher.

In the API directory, run release commands against the intended database:

    python -m pip install -r requirements.txt
    python manage.py check --deploy --settings=config.settings
    python manage.py migrate --noinput --settings=config.settings
    python manage.py createcachetable --settings=config.settings
    python manage.py collectstatic --noinput --settings=config.settings
    # For a fresh installation only; existing edits are preserved:
    python manage.py seed_website --settings=config.settings

Start with the existing Procfile (gunicorn config.wsgi). Set the hosting
provider's service root to perpetual-api. WhiteNoise serves compressed,
fingerprinted files generated by collectstatic. Source assets stay in static/;
uploads use Cloudinary. Back up PostgreSQL and media, and verify a restore before
launch. Schedule python manage.py clearsessions daily.

The database-backed cache shares Django throttle counters between workers.
Django's application throttling is not a substitute for ingress rate limiting.
Frontend requests share a server IP; tune aggregate limits for expected traffic.

HTTPS redirects, secure cookies and one-year HSTS apply in production. Set
TRUST_PROXY_HEADERS=True only when ingress strips and overwrites client-supplied
X-Forwarded-Proto and the application is not directly reachable. Next.js should
call the HTTPS API origin. /health/ is a liveness endpoint exempt from HTTPS
redirects; it reveals no environment or database details and does not test DB health.
Allow the health probe's Host in ALLOWED_HOSTS. API documentation and the DRF
browsable API are disabled in production.

HSTS_INCLUDE_SUBDOMAINS and HSTS_PRELOAD deliberately default to false.
Django deployment checks report W005/W021 until these are enabled; do so only
after confirming every affected subdomain supports HTTPS and choosing browser
preloading. These warnings are not silenced. Database SSL defaults to required;
turn it off only on an explicitly trusted private database connection.

## Next.js service

Use a maintained Node.js version compatible with the installed Next.js package.
Set the service root to perpetual-web, populate .env.production.example values
in the hosting environment, then:

    npm ci
    npm run lint
    npm run typecheck
    npm run build
    npm run start

API_BASE_URL must be explicit; NEXT_PUBLIC_SITE_URL must be the real HTTPS
canonical origin at build time. Set both at runtime too. Never publish localhost
as the canonical site. Do not deploy .env.local from your development machine.
With multiple replicas, use the same build and a shared
NEXT_SERVER_ACTIONS_ENCRYPTION_KEY (a base64-encoded 32-byte key) across instances.
Preserve the browser Host/Origin through the reverse proxy for Server Actions.

Tokens remain in HttpOnly, Secure, SameSite=Lax cookies. Account/editor data is
uncached and authorization is verified by Django. Sign-out clears cookies;
copied stateless JWTs remain valid until expiration. Media optimization accepts
Cloudinary; local media forwarding is for development. API failures produce
controlled messages rather than exposing server errors.

## Release verification

    # API
    ruff check .
    ruff format --check .
    python -m pip check
    python manage.py test --settings=config.local
    python manage.py makemigrations --check --dry-run --settings=config.local
    # Website (with a local API and frontend)
    npm run test:e2e

Browser tests mutate local fixtures: never point them at production. Verify
public desktop/mobile navigation, direct staff login and logout, non-staff
denial of content writes, contact delivery, Cloudinary uploads, HTTPS redirects,
static admin assets and backups in staging before switching DNS.

This repository prepares the applications; hosting, real domain/secret values,
database/cache-table creation, email delivery and ingress protections must be
configured and verified for the actual deployment.

## Resend and security configuration

Configure only the API service with `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, and `HOST_EMAIL`.
The sender must use a domain verified in Resend. SMTP credentials (`EMAIL_USER`, `EMAIL_PASS`,
`EMAIL_HOST_*`) and custom `RESEND_API_URL` are no longer used. No credentials are copied
from PendezaConnect. Django notifications, framework email, and website contact requests all
use this single Resend backend; the web app calls Django and never receives the Resend key.
Production startup rejects missing mail settings. Verify actual delivery in staging with an
approved recipient; automated tests mock the provider.

The website requires HTTPS for both production `API_BASE_URL` and `NEXT_PUBLIC_SITE_URL`.
All mutating web requests must include the exact public Origin. Preserve that header at ingress.
CSP uses fresh script nonces, so pages render dynamically and are private/no-store. Inline styles
remain allowed for existing components; injected scripts are blocked. Local `/media/` proxying
is disabled in production, where media must come from Cloudinary. Server Action payloads are
limited to 256 KB; larger media uploads continue through Django admin.

Django ignores untrusted forwarded IPs for application throttles. Enforce per-client limits on
admin login, registration, token endpoints, contact and newsletter requests at ingress; Next.js
traffic otherwise shares the server's throttle budget. Application cache throttles are not a
replacement for ingress protection against distributed attacks.


## Client portal and email delivery records

Apply the `accounts` migrations before deploying this release. The local database was backed
up before applying migrations 0004 and 0005. The portal lives at `/account`; client registration
and login use the existing password/JWT flow. Staff still land at `/account/content` after login
and can visit `/account` for their own inbox.

Each client sees only their own notification inbox, read/unread state, email copies, and inquiries
submitted while authenticated. Existing guest inquiries are not linked by email address, since
an unverified signup must not gain access to someone else's historical messages. Inboxes show
the latest 50 records and refresh when reopened or when Refresh inbox is selected. This is an
application notification inbox and outgoing email history, not an IMAP mailbox.

In Django admin, add a Portal notification for a client and optionally select Email requested.
Use Portal services to publish available and coming-soon service announcements. The seeded
project workspace, support desk, and billing cards are explicitly future services; they do not
claim to provide those features today.

Email deliveries record each recipient separately, provider acceptance, provider ID, attempts,
and a sanitized failure reason. Only the client copy appears in the client's portal. Provider
acceptance is not proof of inbox delivery; there is no delivery-webhook integration in this release.
The contact form distinguishes a saved inquiry from successful email submission. Failed notifications
can be retried from Django admin or with a targeted command:

    python manage.py retry_email_notifications --contact-id CONTACT_ID --settings=config.settings
    python manage.py retry_email_notifications --delivery-id DELIVERY_ID --settings=config.settings

These commands send mail; select only the intended record. Already accepted messages are skipped,
and retries reuse their persisted Resend idempotency key. No automatic retry worker is scheduled.
A sending attempt interrupted for over five minutes can be retried by the command.

### Local Resend test sender

Until Perpetual Labs has a verified domain, `.env` uses
`RESEND_FROM_EMAIL="Perpetual Labs <onboarding@resend.dev>"`. Resend limits this test sender to
the email address on its account. It cannot support arbitrary client confirmations. For production,
verify your own domain in Resend and replace `RESEND_FROM_EMAIL` with an address on that domain,
then restart Django so the environment is reloaded. Never use another organization's sender domain.
The API key remains server-side. Domain-read access is unnecessary for sending-only keys.
